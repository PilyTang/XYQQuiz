# 驱动联合验证后改用平面 WebCodecs 预览

实机验证发现，RTX 5080 当前驱动上的 Windows Graphics Capture、D3D11 视频处理器与 Media Foundation NVIDIA H.264 MFT 在持续并发时会发生驱动级互等：先激活编码器会停止 WGC 帧回调，先启动 WGC 则编码器首个输入可能永久阻塞。单独的 H.264 编码自检能够成功，因此它不足以证明完整预览链路可用。

当前稳定实现不再把 H.264 作为预览传输的必要条件。通用路径将画面缩放到最大 1024 像素宽并转换为 I420，通过本机 WebSocket 发送，由 WebView2 WebCodecs `VideoFrame` 直接绘制；原生硬件路径使用 WGC 与 D3D11 生成 NV12，同样作为完整平面帧发送。两种路径都只保留最新帧，识别继续使用独立的 15/5 Hz 节拍。

这个决定替代 ADR 0001 与 ADR 0002 中关于“必须使用 H.264、关键帧恢复和 CPU 回退继续使用 JPEG”的部分，其余关于独立原生进程、30 FPS、最大 1024 像素宽、运行时回退、设置可见性和发布门禁的决定保持不变。

原始平面帧增加本机 WebSocket 带宽，但在 1024×576、30 FPS 的典型场景约为 26.5 MB/s，不引入网络传输。发布门禁必须同时统计 Python、辅助进程和 WebView2 的 CPU、内存带宽、Canvas FPS 与预览延迟；如果平面帧路径不能达到目标，后续可以重新评估经过完整 WGC 并发门禁的硬编码实现，不能仅凭孤立编码自检启用。
