# 硬件预览使用低延迟视频流

XYQQuiz 的 Windows 硬件预览后端使用硬件编码的低延迟 H.264 视频流向 WebView2 传送画面，答案框继续作为独立图层叠加；CPU 预览后端保留现有 JPEG 流作为安全回退。H.264 编码块通过现有本机 WebSocket 安全边界发送，由 WebView2 WebCodecs 解码并绘制，不增加 MSE 媒体缓冲或 WebRTC 信令、抖动缓冲和网络协商。预览采用最新画面优先策略：正常情况下维持 30 FPS，积压时跳过过期的呈现结果，严重积压时通过新的关键帧恢复，不能为了播放每一帧持续增加延迟。选择这条链路而不是继续逐帧 JPEG，是因为 30 FPS 下的 CPU 缩放与 JPEG 编码已经成为常驻占用的主要来源，而仅把缩放搬到 GPU 不能消除 CPU 编码成本。首版不增加 HEVC、AV1、MSE 或 WebRTC 分支。

## Consequences

从游戏帧捕获到 WebView2 Canvas 完成绘制的预览延迟，常态目标不超过 50 ms，P95 不超过 100 ms。超过门槛时必须追赶最新画面；未达到门槛的硬件预览后端不得进入自动后端策略的候选集合。

自动后端策略只在相同画面和相同 30 FPS 条件下，硬件预览相对于 CPU 预览将 `XYQQuiz` 与其 WebView2 子进程的总 CPU 占用降低至少 20% 时选择硬件预览。该降幅不能通过降低预览帧率、可读画质或放宽延迟门槛取得；未达到自动选择门槛但通过可用性自检的后端仍允许用户手动选择。

首版 CPU 与硬件预览使用相同的最大 1024 像素宽和 30 FPS 规格进行基准；硬件后端在 GPU 上完成缩放，H.264 码率自动配置，游戏文字可读性不得低于当前 JPEG 预览。发布验收使用包含小号界面文字、题目和选项的固定真实画面，在目标分辨率下比较 JPEG 基线与解码后的 H.264 画面；预定义文字区域的规范化 OCR 结果必须一致，并通过并排人工检查排除明显拖影、色块和文字边缘损失。首版不增加原生分辨率、码率或画质设置。

硬件预览在运行中持续失败时允许紧急热回退 CPU 预览，以保证答题功能继续可用。回退不覆盖用户保存的选择，本次运行不再自动切回硬件后端；界面必须低调但持续显示实际预览后端、实际帧率和可查看的回退原因。

硬件预览只在默认 pywebview + WebView2 桌面模式中提供。用户主动使用 `--external-browser`，或桌面模式因 WebView2 缺失和初始化失败退回外部浏览器时，使用现有 CPU JPEG 预览，不把外部浏览器的 WebCodecs、硬件解码和后台标签页行为纳入支持与验收矩阵。

右侧栏标题下方提供紧凑的运行后端状态，例如 `OCR DirectML · 预览 硬件 · 29.8 FPS`。其中 FPS 是 WebView2 Canvas 的实际绘制帧率；详细采集、编码、解码帧率和预览延迟只在悬停或诊断视图中展示，正常状态不使用醒目颜色。
