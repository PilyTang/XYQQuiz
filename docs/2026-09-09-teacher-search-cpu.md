# 教师节题面搜索 CPU 优化

## 原因

运行中 0.4.3 的三段 5 秒采样显示主进程占整机 CPU 约 5.5%～5.6%，原生硬件预览仅约 0.08%～0.20%。非阻塞堆栈采样中，581/608 个样本集中在教师节全画面多尺度 `matchTemplate`；协调线程自身占整机约 5.0%。

原逻辑对最大 1280 像素宽画面按 12 档尺度搜索。标题单点达到阈值就设置 `suspected`，容易将普通界面误标为疑似教师节，造成反复搜索并阻止科举分流。

## 修改

- 全局搜索先将图像缩到最大 640 像素宽，仅提名候选区域。
- 每个尺度保留最多三个不重叠峰值，再在原始分辨率的小区域内细化尺度并验证。
- 粗搜索低阈值不作为接受依据；标题、退出按钮、提示语仍通过原有精确匹配阈值。
- 缓存缩放模板，上限 128 项，避免每次重新缩放。
- 疑似状态至少需要标题与第二个锚点共同支持；缺少退出按钮但仍有提示语的部分题框继续受到保护。
- 已定位题框维持原有局部追踪；消失/移动先使旧位置失效，再重新定位。没有降低预览帧率或新题扫描频率，也没有加入等待数秒的无题退避。

## 验证

当前游戏窗口的 15 帧画面，仅保存在本机；两版读取相同帧，每帧全局搜索各重复五次：

| 指标 | 0.4.3 | 优化后 |
| --- | --- | --- |
| 每帧中位耗时的中位数 | 199.36 ms | 63.88 ms |
| 每帧中位进程 CPU 时间的中位数 | 203.13 ms | 62.50 ms |
| 错误标记为疑似教师节的帧数 | 15/15 | 0/15 |

这证明该热点计算成本下降约 68%，不等同于运行中程序整体 CPU 已降至某个百分比；没有替换或重启用户正在使用的程序。当前普通画面的科举搜索仍有成本，整体效果需要换用试用包后在同场景再次采样。

另有 6 个由真实锚点组成的正向画面（1024～3840 宽度、不同题框尺度），以及 12 个历史画面，总计 33 帧对比，接受/拒绝结果没有变化。专项覆盖 0.5 倍小题框、2K/4K、从无题到有题、移动重定位、关闭清除、标题单锚点干扰、局部缓存和四题 OCR 回归。

全量测试：686 passed、3 skipped。原始截图不入 Git。复现工具：`scripts/benchmark_teacher_layout_search.py --baseline-ref v0.4.3 --images <本地截图目录> --output <本地报告文件>`。
