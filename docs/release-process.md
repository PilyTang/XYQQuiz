# 正式发布流程

## 何时执行

只有用户明确要求“发布正式更新”“正式发布”“发布正式版 0.x.x”等同等明确的正式发布指令，才启动本流程。普通修复、诊断、开发、测试、本地打包、制作试用包不触发正式发布，也不自动升级版本或改动线上版本信息。

单独要求推代码、上传某个平台、配置测试版本时，只执行明确指定的范围，不扩展为正式双平台发布。既往正式发布授权不延续到下一次修改。本规则的编写或更新也不是发布授权。

明确授权正式发布后，应连续完成下列步骤，不逐项重复请求确认。只有缺少必要信息/凭据、远端版本冲突或其他实际阻塞时，才说明原因并请求补充。

## 1. 确定版本并更新项目说明

- 核对当前源码、远端分支、已有标签和两个平台的发布状态；保留用户未提交的修改。
- 使用用户指定版本；未指定时按变更选择正式版本。已经对外发布的版本默认不覆盖。只有用户明确要求同版本替换时才允许覆盖，并先备份旧 ZIP、校验文件及线上版本清单。
- 同步应用版本、`pyproject.toml`、PE 文件版本、打包脚本默认版本和版本一致性测试；不把版本更新遗漏在某一处。
- 更新 `README.md` 的当前功能、版本及下载/使用说明，更新 `CHANGELOG.md`，新增 `docs/releases/v<版本>.md`。
- 同步 `packaging/README.txt`、开发交接和受影响的专题说明。只写实际完成的功能及真实验证范围，不把历史测试结果当成本版结果。

## 2. 验证源码与发布内容

- 完成与修复相关的回归；正式发布需要完整测试和公开内容审计。可以复用同一提交已经通过的检查或 GitHub CI，不为重复确认无变化的内容反复运行全量测试。
- 执行 `git diff --check` 和公开内容审计，排除私人完整游戏截图、凭据、用户配置、日志、诊断及本地补题。
- 本地检查与真实游戏验收分别说明；未做的系统/设备/活动现场验证不得写成已通过。

## 3. 同步 GitHub 代码和说明

- 将本次代码、版本、README、更新日志和发布说明同步到 GitHub：`https://github.com/PilyTang/XYQQuiz`。
- 检查远端状态，按现有分支协作方式推送或合并；不以强推覆盖远端新增提交。
- 等待发布提交的 CI 通过。不能把仅本地提交或仅上传安装包称为完成 GitHub 同步。

## 4. 构建并发布 GitHub Release

- 从干净的发布提交构建，清单记录完整 Git SHA；标签、应用版本、PE 版本和发布说明一致。
- 生成一份 Windows x64 便携 ZIP 和同名 `.sha256`。将这份产物作为两个平台共用的正式包。
- 完整解压到新目录，验证 EXE 版本、构建清单、资源与 headless 自检，检查中文/空格路径。自检跳过实时捕获时如实记录。
- 在 GitHub 创建 `v<版本>` 标签和正式 Release，使用本次更新说明，上传 ZIP 与 SHA-256，并确认它是最新正式版而非草稿或预发布版。
- 可以先上传草稿，等 CI 通过后公开。选择一次本地构建或一次 CI 构建作为产物来源；不要让两个平台分别重打包导致同版本哈希不同。
- 使用既有标签工作流时，由其构建和发布；使用已验证本地包同步时，不再重复触发另一条构建/上传路径。已有 Release 不盲目重建，先核对标签和附件。

## 5. 发布 CNB

- 发布到 `https://cnb.cool/pilytang/XYQQuiz`，上传与 GitHub 完全相同的 ZIP 和 SHA-256，同步正式发布标题和说明。
- 使用 `scripts/publish_cnb.py`。它包含 CNB 附件发布和下一步版本清单更新；若 GitHub 工作流已经自动同步成功，不再手动重复上传。
- 使用个人访问令牌，权限包括目标仓库的 `repo-code` 和 `repo-release` 读写；部署令牌只有读取能力，不能发布。
- 凭据放在仓库外私有文件或已授权的 CI Secret，运行时读取，禁止写入项目规则、代码、安装包、日志或聊天输出。
- 若同名版本曾用于测试，核对并替换测试附件和说明，同时将名称、草稿/预发布标记恢复为正式发布状态。不得只更改版本号却留下测试包。
- 匿名下载附件并核对完整 SHA-256，确认普通用户可获取正确文件。

## 6. 最后更新 CNB 的 latest.json

用户所说的“lastjson”对应实际文件 **`latest.json`**，位于 CNB 发布仓库的 `main` 分支。客户端读取：

`https://cnb.cool/pilytang/XYQQuiz/-/git/raw/main/latest.json`

- 只有正式附件发布完成且匿名下载校验通过后，才更新该文件，避免先提示新版而下载尚未就绪。
- 内容包括 `schema_version`、正式 `version`、更新说明 `notes`、固定 Release `download_url` 和实际 ZIP 的 `sha256`。
- 版本、下载路径、文件名和 SHA-256 必须对应同一份正式包；不使用会到期的签名跳转地址作为固定下载链接。
- `scripts/publish_cnb.py` 会在校验附件之后提交并验证 `latest.json`；不要绕过其先附件、后版本指针的顺序。
- 临时线上测试需另有明确授权，并备份正式清单；测试结束后恢复清单和发布状态，处理测试客户端缓存，避免留下假版本提示。

## 7. 最终核对与交付

- GitHub 代码和说明已同步、CI 通过；标签对应发布源码提交。
- GitHub 与 CNB 均为正确的正式版本，标题/说明/附件无测试残留。
- 本地、GitHub、CNB 的 ZIP SHA-256 相同；两个平台均提供校验文件。
- 匿名读取线上 `latest.json`，使用客户端检查逻辑验证当前版和旧版的判断结果。
- 回复正式版本号、本地包路径、GitHub Release 和 CNB 下载链接，以及验证结果和未完成的验收边界。
- 某一步失败时明确报告已完成和未完成的部分，保留可恢复状态，不声称整套发布已完成。
