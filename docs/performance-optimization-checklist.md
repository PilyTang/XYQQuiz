# XYQQuiz 后续性能与识别速度优化 Checklist

更新时间：2026-07-26

基线提交：`2a70b31 perf: throttle OCR capture callbacks`

## 目标

在不降低题目识别精度、布局兼容性和 OCR 输入质量的前提下，逐项降低 CPU 占用并缩短新题触发与布局定位耗时。每次只实施一个可独立验证的改动，测量通过后再进入下一项。

## 当前实测基线

- 原生预览保持约 `30 FPS`。
- 30 秒真实游戏场景进程树 CPU：约 `1.67%`。
- Python 主进程 CPU：约 `1.44%`。
- 原生预览助手 CPU：约 `0.13%`。
- WebView2 CPU：约 `0.10%`。
- 优化后 20 秒函数采样中，布局检测与模板匹配约占 Python 活跃 CPU 的 `89.9%`；WGC 回调与颜色转换约占 `2.2%`。
- 当前本地 `config.json` 的 `layout_paths` 为 `null`，只启用 `keju-default`；正式性能基线必须先恢复并验证默认的四套布局，避免用兼容性缩水换取低占用。

## 不可退让的精度约束

- [ ] 保留 5 FPS 完整识别扫描作为最终兜底。
- [ ] 保留全部正式布局配置，不通过删减布局降低耗时。
- [ ] OCR 继续使用原始分辨率题目和选项区域。
- [ ] 不降低布局分析分辨率，不放宽或降低匹配阈值。
- [ ] 快速检测只能触发完整识别，不能单独否决题目存在。
- [ ] 缓存或布局复用失效时必须自动退回完整检测。
- [ ] 每项改动都必须通过完整自动化测试和可用的识别样本回归。

## 优化项目总表

评分说明：实现难度 `1` 最低、`5` 最高；可行性 `5` 最高。性能提升指 CPU 占用下降。

| 状态 | 优化方向 | 预计性能提升 | 预计识别速度提升 | 实现难度 | 可行性 | 备注 |
|---|---|---:|---:|---:|---:|---|
| [ ] | 恢复四套布局并建立完整基线 | 非优化项 | 非优化项 | 1/5 | 5/5 | 所有后续比较的前置条件 |
| [ ] | 缓存不同分辨率的缩放锚点模板 | 约 3–8% | 单次节省数毫秒 | 1/5 | 5/5 | 分辨率或 DPI 变化时清空缓存 |
| [ ] | 已定位后复用布局坐标 | 答题期间约 20–40% | 第二题以后明显加快 | 3/5 | 5/5 | 面板关闭、题型或窗口变化时失效 |
| [ ] | GPU 生成同规格分析缩略图 | 约 10–25% | 布局预处理预计快 5–20ms | 3/5 | 4/5 | 保持现有 1600 像素分析规格，OCR仍用原图 |
| [ ] | GPU 30 FPS 疑似面板检测，5 FPS完整兜底 | CPU持平或小幅下降 | 平均触发等待约 100ms→17ms；最坏约 200ms→33ms | 4/5 | 4/5 | 快速路径只能触发，不能否决 |
| [ ] | 多布局按历史状态智能排序 | 四套布局时约 5–20% | 中等 | 3/5 | 4/5 | 低置信度时必须继续扫描剩余布局 |
| [ ] | 原生助手提供题目/选项 ROI | 约 5–15% | 小到中等 | 4/5 | 3/5 | 当前 WGC 已非主要热点，优先级较低 |
| [ ] | GPU 模板匹配 | 总 CPU 可能再降 30–50% | 布局阶段预计快 30–60% | 5/5 | 3/5 | 需要验证与 OpenCV 结果的一致性及不同显卡 |

## 推荐实施顺序

### 0. 恢复完整兼容性基线

- [ ] 让实际运行配置启用正式四套布局。
- [ ] 确认现有题型、图片题和已保存诊断样本的识别结果不变。
- [ ] 重新记录 30 秒 CPU、预览 FPS、布局耗时和端到端耗时。
- [ ] 将结果填写到本文件的“实测记录”。

### 1. 缓存缩放锚点模板

- [ ] 缓存键包含布局、锚点、目标尺寸、分辨率和 DPI。
- [ ] 分辨率、DPI 或布局配置变化时清空缓存。
- [ ] 对比缓存前后模板匹配输出和置信度，要求一致。
- [ ] 运行完整测试并记录 CPU 与布局耗时变化。

### 2. 已定位后复用布局

- [ ] 明确定义布局缓存的建立、复用和失效条件。
- [ ] 面板关闭、窗口移动、分辨率变化和题型变化会立即失效。
- [ ] 保留定期完整检测，避免长期使用陈旧坐标。
- [ ] 验证第一题、连续换题、图片题和退出答题流程。
- [ ] 记录第一题与后续题的触发和布局耗时。

### 3. GPU 分析缩略图

- [ ] 原生助手按当前算法规格生成分析帧。
- [ ] 验证尺寸、颜色空间、插值方式和坐标恢复一致。
- [ ] 完整分辨率原图仍保留给 OCR 和框选。
- [ ] 对同一批样本比较 CPU、布局耗时和检测结果。

### 4. 30 FPS 快速触发与 5 FPS 完整兜底

- [ ] 快速检测只产生“立即完整识别”的触发信号。
- [ ] 即使快速检测未触发，5 FPS 完整扫描仍照常运行。
- [ ] 记录触发等待时间的 P50、P95 和最坏值。
- [ ] 验证快速检测误报不会产生错误框选或答案。

### 5. 后续可选项目

- [ ] 评估多布局排序是否在四套布局基线下仍有明显收益。
- [ ] 仅当帧复制重新成为热点时实施原生 ROI 传输。
- [ ] 仅当前述项目仍无法达到目标时实施 GPU 模板匹配。

## 每项统一验收标准

- [ ] 完整自动化测试通过，跳过项原因可解释。
- [ ] `git diff --check` 通过。
- [ ] 原生预览稳定在目标帧率附近，无新回退或关闭错误。
- [ ] 识别样本的题目、选项、答案和框选结果不退化。
- [ ] 使用同一游戏窗口、分辨率、场景和采样时长比较 CPU。
- [ ] 分别记录 Python、原生预览助手、WebView2 和总进程树 CPU。
- [ ] 区分普通游戏场景、答题面板出现和连续换题三种状态。
- [ ] 结果通过后创建独立 Git 提交，再开始下一项。
